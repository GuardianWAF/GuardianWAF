# GuardianWAF v0.6.0 — Distributed Coordination & Advanced Routing

**Status:** Planning
**Target:** Q4 2026
**Predecessor:** [v0.5.0 — Detection Expansion](./v0.5.0-roadmap.md)

---

## Theme

v0.5.0 closed the detection coverage gap. v0.6.0 closes the **operational scale gap**: multi-node deployment, cross-node state synchronization, canary traffic shifting, and production-grade observability for distributed WAF fleets.

The core architectural constraint from v0.5.0 carries forward: **zero external dependencies**. The consensus protocol, gossip layer, and canary router will all be built from Go standard-library primitives.

---

## Prioritized Features

### P1: Cluster Sync (Gossip-based state replication)

**Why:** A multi-node GuardianWAF deployment currently has no way to share IP bans, rate-limit counters, custom rules, or tenant configuration across nodes. An attacker banned on node A can immediately retry on node B.

**Design:**

- **Protocol:** SWIM (Scalable Weakly-consistent Infection-style Process Group Membership) gossip protocol, built from `net` and `crypto/tls`.
  - No external dependency — pure Go implementation using `net.PacketConn` (UDP) for gossip probes and `net.TCPListener` for state transfer.
  - Failure detection: indirect probes with suspicion state (alive → suspect → dead).
  - State dissemination: piggyback on heartbeat probes; full-state sync on join.
- **Replicated state:** IP bans (with TTL), rate-limit counters (eventually consistent), custom rules, tenant configs.
- **Conflict resolution:** Vector clocks with `last-write-wins` per key (configurable: `last_write_wins`, `source_priority`, `manual`).
- **Package:** `internal/cluster/gossip/` (implemented — SWIM-style membership with UDP transport, 26 tests, race-clean). `internal/cluster/raft/` (planned — does not exist in v0.5.0 tree).
- **Config:** `waf.cluster.enabled`, `waf.cluster.config.bind_addr`, `waf.cluster.config.peers`, `waf.cluster.config.gossip_interval`.
- **Dashboard:** Wire existing cluster handler stubs (`internal/dashboard/cluster_handlers.go`) to live cluster state. Show node list, health, sync stats.

**Key design decisions:**

| Decision | Choice | Rationale |
|---|---|---|
| Consensus model | Gossip (SWIM) not Raft | WAF state is eventually consistent — IP bans and rate-limit counters tolerate seconds of lag. Raft's strong consistency is unnecessary overhead for this use case. |
| Transport | UDP for gossip, TCP for state transfer | UDP for low-overhead heartbeats; TCP for reliable bulk state sync on join/rejoin. |
| Membership | SWIM with suspicion | Avoids false-positive node removal during transient network partitions. |
| State size cap | 10,000 keys per namespace | Bounds memory and sync time. Auto-eviction of expired bans is the natural compaction. |

**Effort:** ~10 days (SWIM protocol, state store, conflict resolution, TLS auth, tests, dashboard wiring)

**Test evidence target:** `go test ./internal/cluster/...` (planned package — does not exist in v0.5.0 tree)

### P2: Canary Routing

**Why:** Operators need to route a percentage of traffic to a new upstream version (canary) for safe rollout, then progressively shift weight or auto-rollback on error-rate spike. This depends on cluster sync for cross-node consistent routing decisions.

**Design:**

- **Weighted canary:** Extend `TargetConfig` with a `canary: true` flag. The existing `Balancer` already supports weighted round-robin — canary targets get a configurable percentage.
- **Progressive rollout:** `canary_weight` starts at 5%, operator increases via dashboard API or config reload. No traffic redistribution mid-request.
- **Auto-rollback:** Monitor canary target error rate. If error rate exceeds threshold (default: 5%) over a sliding window (default: 60s), automatically drop canary weight to 0% and fire an alert.
- **Session affinity:** Optional sticky canary — `Cookie: gwaf-canary=v1` pins a client to the canary target for consistent A/B testing.
- **Metrics:** `guardianwaf_canary_requests_total{target,version}`, `guardianwaf_canary_error_rate{target}`, `guardianwaf_canary_weight{target}`.
- **Package:** Can be implemented in `internal/proxy/` (extend existing `Balancer`) — no new top-level package needed.
- **Config:**
  ```yaml
  upstreams:
    - name: my-service
      targets:
        - url: "http://v1.example.com"
          weight: 95
        - url: "http://v2.example.com"
          weight: 5
          canary: true
      canary_policy:
        auto_rollback: true
        error_rate_threshold: 0.05
        evaluation_window: "60s"
        min_requests: 100
  ```

**Key design decisions:**

| Decision | Choice | Rationale |
|---|---|---|
| Weight distribution | Per-target weight (existing Balancer) | The Balancer already supports `weighted` load balancing. Canary is just a target with `canary: true` and a lower weight. No new routing logic needed. |
| Rollback trigger | Error rate (5xx + timeouts) | Response latency is noisy; error rate is a clear signal. `min_requests` prevents false rollback at low volume. |
| Session pinning | Cookie-based (opt-in) | Header-based pinning breaks when the client is a browser. Cookie is transparent to the application. |
| Cross-node consistency | Eventually consistent via cluster sync | Canary weight changes propagate via gossip within seconds. Mid-rollout inconsistency is acceptable — some nodes route 5%, others 8% briefly. |

**Effort:** ~5 days (weight logic, auto-rollback monitor, metrics, dashboard controls, tests)

**Test evidence target:** `go test ./internal/proxy/...` (existing package — extend with canary tests)

### P3: Advanced Observability (Distributed Tracing)

**Why:** In a multi-node deployment, tracing a single request's path through the WAF → upstream → response is critical for debugging. The existing `X-Correlation-ID` propagation is a start, but structured tracing (OpenTelemetry-compatible spans) is needed for production debugging.

**Design:**

- **Span model:** `waf.request` (root), `waf.layer.<name>` (per-layer), `waf.proxy.upstream` (backend call).
- **Export format:** OTLP-compatible JSON over HTTP (no OpenTelemetry SDK dependency — hand-rolled JSON matching the OTLP HTTP protocol spec).
- **Sampling:** Configurable rate (default: 1% of requests, 100% of blocked requests).
- **Config:** `tracing.enabled`, `tracing.endpoint`, `tracing.sample_rate`, `tracing.always_sample_blocked`.
- **Package:** Extend existing `internal/engine/tracing.go` — no new package.

**Effort:** ~3 days (span generation, OTLP JSON encoder, sampling logic, tests)

### P4: Hot Config Reload Without Restart

**Why:** Currently, config changes require a process restart. In a multi-node cluster with rolling deploys, this means brief availability gaps. Hot reload eliminates the gap and enables cluster-wide config push (via cluster sync).

**Design:**

- **File watcher:** `fsnotify`-equivalent using `os.Stat` polling at 2s intervals (no external dependency). Detect mtime changes, re-parse YAML, validate, swap atomically.
- **Layer diff:** Compare old and new config. Only rebuild layers whose config changed. Layers that didn't change keep their runtime state (caches, counters, ban lists).
- **Atomic swap:** Config swap happens under a single `RWMutex` write lock. In-flight requests continue with the old config; new requests get the new config.
- **Graceful layer shutdown:** Layers that are being replaced get `Close()` called after all in-flight requests using them complete.
- **Dashboard:** Show config reload events in the audit log. Provide a manual "Reload Config" button.

**Effort:** ~4 days (file watcher, diff engine, atomic swap, graceful shutdown, tests)

## Architectural constraints (carry forward from v0.5.0)

1. **Zero external dependencies.** The SWIM gossip protocol, OTLP trace exporter, and canary router will all use only the Go standard library. No `hashicorp/memberlist`, no `open-telemetry/opentelemetry-go`, no `fsnotify/fsnotify`.

2. **Layer isolation.** Cluster sync hooks into the engine via existing interfaces (`EventBus` subscriber, `Layer.Process`). No changes to the engine's core pipeline logic.

3. **Multi-tenancy.** Cluster sync replicates per-tenant state. Canary routing supports per-tenant upstream targets. Tracing includes `tenant.id` as a span attribute.

4. **Performance budget.** New layers must not exceed the existing pipeline overhead budget. The benign-request path must stay under 25µs (currently 23µs with 11 detectors). Gossip probes run in background goroutines — zero impact on request path.

5. **Config validation.** All new config fields must be validated in `validate.go` with clear error messages. Deepcopy must be regenerated.

## Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Gossip protocol complexity causes stability issues | Medium | High | Start with 2-node simple sync, add SWIM sophistication incrementally. Extensive chaos testing with network partitions. |
| Cluster sync creates a performance regression on the request path | Low | High | Gossip runs in background goroutines. Request path only reads from a `sync.RWMutex`-protected state map. Benchmark before and after. |
| Hot reload introduces race conditions | Medium | Critical | All config access goes through atomic pointer swap. In-flight requests hold a reference to the old config. `-race` detector on all tests. |
| OTLP JSON format drifts from spec | Low | Medium | Validate exported spans against the OTLP JSON schema. Integration test against a mock collector. |
| Canary auto-rollback triggers on legitimate error spikes | Medium | Medium | Require `min_requests` (default: 100) before evaluating error rate. Operator can disable auto-rollback. Dashboard shows rollback events. |
