## v0.5.0 Scope — "Detection depth + enterprise integration"

### P1: Security (must-have)

#### 1. HTTP Request Smuggling detection
**Package:** `internal/layers/detection/smuggling/`
**Why:** #1 WAF bypass technique — an attacker sends ambiguous `Content-Length`
+ `Transfer-Encoding` headers to make the frontend (WAF) and backend disagree
on request boundaries. This lets malicious requests bypass detection entirely.

**Design:**
- Reject requests with both `Content-Length` and `Transfer-Encoding` headers
- Validate `Transfer-Encoding` is exactly `chunked` (reject `chunked, identity`)
- Reject duplicate/conflicting headers (`CL: 0\r\nCL: 100`)
- HTTP/2 → HTTP/1.1 downgrade smuggling (pseudo-header + CL conflict)
- Config: `detection.smuggling.strict: true` (default: true)

**Effort:** ~2 days (new layer + tests + fuzz target)

#### 2. Open Redirect detection
**Package:** `internal/layers/detection/openredirect/`
**Why:** Protects callback/redirect endpoints from being weaponized for
phishing. Attackers abuse `?redirect_uri=` parameters to bounce victims
through legitimate domains.

**Design:**
- Scan query parameters matching redirect patterns (`redirect`, `url`,
  `next`, `return`, `callback`, `goto`, `dest`, `target`)
- Detect absolute URLs, protocol-relative URLs (`//evil.com`), and
  backslash-encoded URLs (`\/evil.com`)
- Config: `detection.openredirect.params: [redirect, url, ...]`
- Whitelist domains via existing `allowed_redirect_domains` list

**Effort:** ~1 day (new layer + tests)

#### 3. GraphQL query depth/complexity limiting
**Package:** extends `internal/layers/apisecurity/`
**Why:** Nested GraphQL queries (`{user{friends{user{friends{...}}}}}`)
cause exponential DB load. A single request can DoS a backend.

**Design:**
- Detect `application/graphql` content-type or `query` POST body
- Parse query depth (count nested `{` levels)
- Enforce max depth (default: 10) and max complexity (field count × depth)
- Config: `apisecurity.graphql.maxDepth: 10`, `maxComplexity: 1000`

**Effort:** ~2 days (parser + integration into existing api security layer)

### P2: Enterprise integration (should-have)

#### 4. SIEM export (CEF over TLS syslog)
**Package:** `internal/layers/siem/` (new layer)
**Why:** Enterprise deployments require WAF events in Splunk/QRadar/Sentinel.
Without SIEM export, GuardianWAF events only live in the dashboard + JSONL file.

**Design:**
- CEF (Common Event Format) — the de facto SIEM standard
- Transport: TLS syslog (RFC 5425) to configurable endpoint
- Only sends block/challenge events (not pass), throttled by rate limiter
- Config: `siem.enabled`, `siem.endpoint`, `siem.format: cef|leef|json`,
  `siem.tls: true`
- Uses existing event store for replay/buffer
- Batch send (1s window or 100 events, whichever comes first)

**Effort:** ~3 days (CEF formatter + TLS syslog client + batching + tests)

#### 5. WebSocket message inspection
**Package:** `internal/layers/websocket/` (new layer)
**Why:** WebSocket traffic currently bypasses all detection. An attacker can
tunnel SQLi/injections through a WS upgrade.

**Design:**
- Hook into existing reverse proxy's `Upgrade` handling
- Frame-level inspection: decode text frames, run sanitizer + detection layers
- Config: `websocket.inspect: true`, `websocket.max_frame_size: 1MB`
- Binary frames: size-limit only (no content inspection)
- Origin validation (CSWSH protection)

**Effort:** ~3 days (frame parser + detection integration + tests)

### P3: Operability (nice-to-have)

#### 6. Dashboard: real-time event tail (SSE)
**Why:** Security teams need live event visibility for incident response.
Currently the dashboard polls every 5s.

**Design:**
- SSE endpoint: `GET /api/v1/events/stream` (auth-gated, admin-only)
- Subscribes to event store, pushes new events as JSON objects
- Frontend: React `EventSource` hook, auto-reconnect
- Dashboard page: "Live Events" with pause/resume and filter chips

**Effort:** ~1 day (SSE handler + frontend hook)

#### 7. Dashboard: false-positive tuning UI
**Why:** Operators need to create exclusion rules directly from a blocked
event, without editing YAML config.

**Design:**
- "Create Exclusion" button on event detail page
- Pre-fills rule (layer, pattern, parameter, scope)
- Writes to `custom_rules` via existing PUT config API
- Scope: per-tenant or global

**Effort:** ~2 days (UI + API integration)

## Architectural constraints

1. **Zero external dependencies.** Every new feature must use only the Go
   standard library. No `graphql-go`, no `gorilla/websocket`, no syslog
   libraries. Build parsers from `net/http` internals.

2. **Layer isolation.** New detection layers implement the existing
   `Layer` interface and register via `OrderedLayer`. No changes to the
   engine's core pipeline logic.

3. **Multi-tenancy.** Every new feature must support per-tenant scoping.
   Detection rules, SIEM destinations, and WS inspection must be
   configurable per tenant.

4. **Performance budget.** New layers must not exceed the existing
   pipeline overhead budget. The benign-request path must stay under
   25µs (currently 23µs). Zero-allocation where possible.

5. **Config validation.** All new config fields must be validated in
   `validate.go` with clear error messages. Deepcopy must be regenerated.
